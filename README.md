# Hydra

**A self-hosted platform for researching, paper-trading and carefully live-trading crypto strategies on Binance.**

Hydra lets you design a trading strategy (with a visual rule builder, YAML or a machine-learning model), test it
honestly on real historical data, run it against the live market with simulated money, and only then, behind a
deliberate arming ceremony, let it trade real funds. Everything runs on your own hardware: a FastAPI engine, a
Next.js dashboard, background workers and a TimescaleDB database.

**What Hydra is**

- A research workbench: backtests, parameter search and walk-forward validation on stored Binance candles, with
  overfitting statistics (Deflated Sharpe ratio, probability of backtest overfitting) instead of one flattering curve.
- A paper-trading engine: strategies trade live Binance market data against a simulated account that follows
  Binance's own rules (balances, fees, order types).
- A live-trading engine for Binance spot and Binance USD⌂-M perpetual futures, off by default and gated by one-time
  codes that a human types.
- An MCP server, so an AI assistant can run research and paper sessions, while every risky action still needs your
  code.

**What Hydra is not**

- Not a hosted service, not a signal seller and not financial advice. It trades only what you configure it to.
- Not multi-exchange: Binance spot and Binance USD⌂-M perps are the only venues.
- Not open source: the code is published for viewing only (see [License](#license)).

> [!WARNING]
> Live trading can lose the capital you allocate to it, and more if a protective stop is rejected or the exchange
> fails. Read the [live-trading guide](docs/live-trading.md) before arming.

## Features

- **Strategy builder.** Compose entry and exit rules from over 30 indicator series (moving averages, RSI, MACD,
  ATR, ADX, Bollinger and Keltner bands, Donchian channels and more) in a visual builder, or write the YAML by hand. Five
  templates to start from. Every strategy carries a stop-loss.
- **Honest backtests.** Backtests replay stored one-minute Binance candles through the same execution code as paper
  trading. Missing history is downloaded on demand; nothing is ever synthesised. Metrics are annualised for 24/7
  markets and compared with buy-and-hold on the same candles.
- **Overfitting checks.** Hyperparameter search keeps a final 20 % holdout no trial ever sees and reports the Deflated
  Sharpe ratio and the probability of backtest overfitting. Walk-forward analysis re-optimises on every window and
  stitches the out-of-sample results.
- **Paper trading.** Sessions trade the live market with a simulated account: fees, slippage, locked balances, stops,
  OCO and trailing orders, filled on closed candles. State survives restarts.
- **Live trading.** Binance spot and USD⌂-M perps (isolated margin, 1-3x leverage), with exchange-side protective
  orders that keep working when Hydra is down, and a reconcile loop that pages on any drift.
- **Machine learning.** Train gradient-boosted models on a walk-forward grid, register immutable versions, promote or
  roll back with a typed confirmation, use a model as a veto on entries or as a strategy of its own, and watch for
  feature drift.
- **Top-100 universe.** New strategies are limited to the 100 Binance USDT pairs with the highest 24-hour volume
  (stablecoins and fiat excluded), ranked and refreshed automatically, with a bounded on-disk cache of candles.
- **Risk controls.** Pre-trade checks, a four-tier drawdown circuit breaker, a daily-loss halt, a loss-streak pause
  and a kill switch, all persisted.
- **Dashboard.** Portfolio, sessions, builder, backtests, optimisation, models, data, risk and an activity trail of
  who did what, usable on a phone.
- **AI assistant access (MCP).** Research, strategy, session, risk and model tools over a bearer-token MCP endpoint.
- **Operations.** Prometheus metrics with alert rules, a Grafana dashboard, liveness and readiness probes, JSON logs.

```mermaid
flowchart LR
    you(["You, in a browser"])
    ai(["AI assistant (MCP client)"])
    binance["Binance<br/>spot and USD-M perps"]

    subgraph stack["Your server (Docker Compose)"]
        dash["Dashboard<br/>Next.js"]
        api["API<br/>FastAPI, auth, MCP server"]
        trader["Trader<br/>sessions, strategies, risk, executors"]
        worker["Backtest worker<br/>backtests, optimisation, ML training"]
        db[("TimescaleDB<br/>candles, sessions, fills, jobs, models")]
        redis[("Redis<br/>health check only")]
    end

    you --> dash
    dash -->|"HTTP and WebSocket"| api
    ai -->|"bearer token"| api
    api -->|"internal API"| trader
    api --> db
    trader --> db
    worker --> db
    trader <-->|"market data and orders"| binance
    worker -->|"download missing candles"| binance
    api -.-> redis
```

- The **API** is the only public surface. Every route except the health probes and metrics needs an authenticated
  caller (a reverse-proxy login, or a bearer token for services); the MCP endpoint exists only when its own token is
  configured.
- The **trader** owns every running session. In the default single-process layout, API and trader run in one
  process; in production they are two containers of the same image, and the database is the only state they share.
- The **backtest worker** runs queued backtests, optimisations and ML training jobs. Jobs are durable: they survive
  restarts, retry, and can be cancelled.

## From candle to order

Every session, paper or live, runs the same loop once per closed candle:

```mermaid
flowchart LR
    bar["Closed candle<br/>from Binance"] --> fills["Fill resting stops<br/>and limits, mark positions"]
    fills --> strategy["Strategy<br/>rules or ML model"]
    strategy -->|"exit signal"| om["Order manager"]
    strategy -->|"entry signal"| veto{"ML veto<br/>(optional)"}
    veto -->|"allowed"| om
    veto -->|"vetoed"| skip(["no order"])
    om --> risk{"Pre-trade risk check<br/>kill switch, breakers, limits"}
    risk -->|"rejected"| skip
    risk -->|"approved"| exec["Executor<br/>paper or live, spot or perp"]
    exec --> stop["Protective stop<br/>with every entry"]
```

Backtests feed stored candles through this same loop with a paper executor, so a backtest and a paper session of the
same strategy make the same decisions. The [paper fill rules](docs/paper-fill-rules.md) describe exactly how
simulated orders fill.

## From idea to live: the research pipeline

```mermaid
flowchart LR
    idea["Strategy<br/>builder, YAML or ML model"] --> bt["Backtest<br/>stored candles only"]
    bt --> opt["Hyperopt<br/>grid or Bayesian search,<br/>20% untouched holdout"]
    opt --> wf["Walk-forward<br/>re-optimise per window,<br/>out-of-sample results"]
    wf --> paper["Paper session<br/>live market, simulated money"]
    paper --> live["Live session<br/>after the arming ceremony"]
    data[("Stored candles")] -.-> bt
    data -.-> opt
    data -.-> wf
```

Each step answers a different question: does the idea work at all (backtest), are the parameters real or lucky
(hyperopt's holdout, Deflated Sharpe ratio and probability of backtest overfitting), does it survive changing market
regimes (walk-forward), and does it behave the same on the live market (paper). Every result records exactly which
candles it ran on.

## Safety model

Hydra assumes things go wrong: the engine crashes, a key leaks, a fat finger hits the wrong button. The defaults
are built around that.

- **Paper by default.** Nothing touches real money until you arm live trading, and arming spot never arms perps.
- **A human types every risky step.** Arming, each live session start, each manual live order and deleting a
  key that can still trade each need a one-time 6-digit code (single use, 10-minute expiry, five wrong attempts). The kill
  switch, stopping a session and disarming are never gated, because they only reduce risk.
- **Trade-only keys.** A key that can withdraw funds is refused when you connect it, and its permissions are
  re-checked live when you arm. Keys are encrypted at rest.
- **No live position without a stop on the exchange.** Every live entry places its protective order on Binance
  immediately. If that fails, the position is closed at market. The stop keeps working while Hydra is down, a check
  on every candle verifies it, and an alert pages on any gap.
- **Layered risk limits.** Pre-trade checks size and cap every order; drawdown tiers cut size, stop new entries,
  flatten every session and finally trip the kill switch; a daily-loss halt and a loss-streak pause sit alongside.
- **Reconcile, never adopt.** Live sessions compare Hydra's books with the exchange every minute and page on a
  deficit. Hydra never adopts orders or positions it did not create.
- **AI assistants get the same gates.** The MCP server can run research and paper sessions freely, but its gated
  actions wait for the code you type in the dashboard.

The arming ceremony for spot (perps follow the same pattern with their own budget and arm):

```mermaid
sequenceDiagram
    actor You
    participant UI as Dashboard
    participant API as Hydra
    participant BN as Binance

    You->>UI: Connect a trade-only API key
    UI->>API: Store key
    API->>BN: Read key permissions
    API-->>UI: Refused if it can withdraw, else stored encrypted
    You->>UI: Arm live trading with a capital budget
    UI->>API: Arm request
    API-->>UI: One-time code
    You->>UI: Type the code back
    UI->>API: Approve with code
    API->>BN: Re-check key permissions
    API-->>UI: Live trading armed (audited)
    You->>UI: Start a live session
    UI->>API: Start request
    API-->>UI: A new one-time code
    You->>UI: Type that code
    UI->>API: Approve with code
    API->>BN: Real orders, each with an exchange-side stop
    Note over You,BN: Kill switch, stop and disarm are never gated
```

The [live-trading guide](docs/live-trading.md) covers the key recipe, the ceremony in detail, what happens when the
engine goes down with positions open, and the residual risks.

## Quick start

Hydra is developed and deployed on Linux and macOS. You need [uv](https://docs.astral.sh/uv/) (0.13.3), Node 26 for
the dashboard, and Docker for the local database.

```bash
# Python dependencies and the unit tests (what CI runs)
uv sync --locked --extra dev
uv run pytest tests/unit -m "not slow"

# TimescaleDB and Redis for local development (Docker)
make dev-up

# The engine (API, trader and sessions in one process) on http://localhost:8000
export DATABASE_URL=postgresql://hydra:hydra_dev@localhost:5432/hydra REDIS_URL=redis://localhost:6379/0
export HYDRA_CREDENTIAL_KEY=$(uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")
uv run python -m hydra.dashboard.api

# The dashboard on http://localhost:3000 (forwards /api to the engine)
cd dashboard && npm ci && npm run dev
```

Keep the credential key: exchange keys stored under it cannot be read with another one. `.env.example` lists every
variable. `make dev` installs every extra, including the ML training libraries; `make install` installs runtime
dependencies only. The engine creates its database schema on first start.

## Configuration

- **Where settings come from.** One validated model, loaded once at startup. Precedence: environment >
  `config/{HYDRA_ENV}.yaml` > `config/base.yaml` > defaults. `HYDRA_ENV` (default `base`) selects an overlay, which
  must exist; `HYDRA_CONFIG_DIR` moves `base.yaml` and the overlay only (`strategies/` and `templates/` are still
  read from the repo or image `config/`).
- **Overrides.** Any key can be set from the environment as `HYDRA_<SECTION>__<KEY>`, for example
  `HYDRA_TRADING__TESTNET=false`, `HYDRA_LOGGING__LEVEL=DEBUG` or
  `HYDRA_API__CORS_ORIGINS=https://a.example,https://b.example`.
- **Infrastructure comes only from the environment**: `DATABASE_URL`, `REDIS_URL`, `HYDRA_CREDENTIAL_KEY`,
  `HYDRA_API_TOKEN` (and `HYDRA_MCP_TOKEN` to enable the MCP endpoint). Putting them, or `database:`, `redis:` or
  `exchanges:`, in YAML is a startup error.
- **Fail fast.** An unknown key at any depth, an unknown or retired `HYDRA_*` variable (the message names the
  replacement, for example `HYDRA_CORS_ORIGINS` -> `HYDRA_API__CORS_ORIGINS`), an unresolved `${VAR}` or an invalid
  value stops startup and names the key, variable or file. Secret values are never printed.
- **The credential key** encrypts exchange keys in the database and is required whenever `DATABASE_URL` is set. It is
  never generated or written to disk. To rotate, set `new,old`, reconnect each exchange in Settings (which
  re-encrypts under `new`), then drop `old`. Rows no configured key can decrypt show as undecryptable and must be
  re-entered.
- **Strategies** are YAML files in `config/strategies/`; the dashboard's builder writes them, and `config/templates/`
  holds the starting points.

## Deployment

Production runs as a Docker Compose stack in the [romulus](https://github.com/somatczk/romulus) homelab repo
(`stacks/hydra/`) on a single Ubuntu server. CI publishes three images to GHCR after every green push to `main`:
`hydra-engine` (the API, and the trader with `command: python -m hydra.trader`), `hydra-dashboard` and
`hydra-backtest` (the worker). A release tag such as `2.9.0` is pushed once and never moves; romulus pins it.

In production the API and the trader are separate containers of the engine image (`HYDRA_TRADER__URL` points the
API at the trader), the dashboard sits behind the same host, and the API sits behind a Traefik reverse proxy with
Authelia login. Prometheus alert rules and a Grafana dashboard live in [`deploy/`](deploy/); the running Prometheus,
Alertmanager and Grafana are in romulus. `deploy/compose.yml` is a local full-stack approximation, not the
deployment.
